# Coolify의 네트워크와 도메인

앱 컨테이너가 실행 중이라는 사실만으로 도메인을 통한 접속까지 보장되지는 않는다. 사용자의 요청이 앱에 도달하려면 DNS, 서버의 접속 경로, 프록시, Docker 네트워크, 앱의 수신 포트가 연결되어 있어야 한다.

이 글은 Coolify가 관리하는 HTTP 프록시를 통해 웹 앱에 접속하는 구성을 설명한다. 예시의 도메인과 주소는 설명용이며 실제 운영 설정이 아니다. 별도 CDN, 로드 밸런서, 터널을 사용하는 환경은 그 구성 요소까지 포함해서 경로를 확인해야 한다.

## 1. 요청이 앱에 도달하는 과정

```text
1. 주소 조회
   브라우저 -> DNS 조회 -> 접속할 IP 주소 확인

2. 서버 접속 및 요청 전달
   브라우저
     -> 서버의 HTTPS 포트
     -> 프록시
     -> Docker 네트워크
     -> Spring 앱의 내부 포트

3. 앱 처리
   Spring 앱
     -> 필요한 경우 DB 조회
     -> 응답을 프록시를 거쳐 브라우저로 반환
```

DNS는 주소를 조회하는 데 사용한다. 조회 후의 HTTP 요청이 DNS 서버를 통과해서 앱으로 전달되는 것은 아니다.

일반적인 Coolify 구성에서 앱 요청을 받는 것은 리소스 실행 서버의 프록시다. Coolify 관리 화면은 이 요청의 중계 지점이 아니다. [공식 문서: Networking in Coolify](https://coolify.io/docs/core/networking-in-coolify)

## 2. DNS는 도메인을 접속 주소로 연결한다

DNS는 도메인 이름에 대한 정보를 조회하는 시스템이다. 웹 접속에서는 도메인에 해당하는 IP 주소를 찾는 데 사용한다.

```text
api.example.com
  -> DNS 조회 결과: 203.0.113.10
  -> 해당 주소로 접속 시도
```

자주 사용하는 주소 레코드는 다음과 같다.

| 레코드 | 역할 |
| --- | --- |
| A | 이름을 IPv4 주소에 연결 |
| AAAA | 이름을 IPv6 주소에 연결 |

DNS 레코드에는 앱의 URL 전체를 입력하는 것이 아니다. A 레코드의 값은 IP 주소이며, `https://`, 포트 번호, `/api` 같은 경로를 포함하지 않는다.

앱 도메인은 앱이 실행되는 서버의 접속 경로를 가리켜야 한다. 관리 서버와 앱 서버가 분리되어 있다면, 앱 도메인을 단순히 Coolify 관리 서버 주소로 연결해서는 안 된다. CDN을 사용하면 공개 DNS에는 CDN의 주소가 보일 수 있으며, CDN에서 실제 앱 서버로 연결되는 설정을 따로 확인한다. [공식 문서: DNS](https://coolify.io/docs/core/networking/dns)

### DNS 변경과 캐시

DNS 응답은 일정 시간 캐시될 수 있다. TTL은 응답을 캐시할 수 있는 시간을 나타낸다. 레코드를 변경해도 기존 응답이 남아 있으면 사용자나 조회 위치에 따라 잠시 다른 주소를 사용할 수 있다.

A와 AAAA가 모두 설정되어 있다면 두 경로가 모두 정상인지 확인한다. IPv4만 정상이고 IPv6 경로가 잘못되어 있으면 일부 접속이나 인증서 발급이 실패할 수 있다. [공식 문서: DNS](https://coolify.io/docs/core/networking/dns)

## 3. 프록시는 요청을 알맞은 앱으로 전달한다

리버스 프록시는 클라이언트의 요청을 받아 뒤쪽의 앱으로 전달하는 프로그램이다. Coolify에서는 설정된 도메인과 경로를 바탕으로 프록시의 전달 규칙을 구성한다.

여러 도메인이 같은 IP 주소를 가리켜도 프록시는 요청의 호스트 이름을 기준으로 앱을 구분할 수 있다.

```text
api.example.com --+
                 +-> 같은 서버의 프록시
web.example.com -+     |
                       +-- api.example.com -> Spring API
                       +-- web.example.com -> 웹 프런트엔드
```

DNS는 어느 주소에 접속할지 알려주고, 프록시는 도착한 요청을 어느 앱에 전달할지 결정한다. 따라서 DNS가 올바르더라도 프록시에 해당 도메인의 전달 규칙이 없으면 원하는 앱으로 연결되지 않는다.

프록시와 대상 앱은 서로 통신할 수 있는 Docker 네트워크에 연결되어 있어야 한다. 같은 Project나 Environment에 속한다는 사실만으로 이 연결이 보장되지는 않는다. [공식 문서: Networking in Coolify](https://coolify.io/docs/core/networking-in-coolify)

## 4. 외부 포트와 앱 내부 포트

포트는 프로그램의 통신 접점을 구분하는 번호다. HTTPS 접속의 기본 포트는 443이고 HTTP는 80이다. 앱이 컨테이너 안에서 사용하는 포트는 이와 달라도 된다.

```text
사용자: https://api.example.com
  -> 서버의 443 포트
  -> 프록시
  -> Spring 컨테이너의 8080 포트
```

이 구성에서는 브라우저가 앱의 8080 포트에 직접 접속하지 않는다. 프록시가 내부 네트워크로 전달하므로 앱의 8080을 서버에 별도로 공개할 필요가 없다.

### Ports Exposes와 Ports Mappings

Dockerfile Application의 Ports Exposes는 앱 내부의 수신 포트에 맞춘다. 앱이 실제로 8080에서 수신하는데 설정이 다른 포트를 가리키면 프록시가 올바른 대상으로 요청을 전달하지 못한다.

또한 앱이 컨테이너 내부의 `127.0.0.1`에서만 수신하면 다른 컨테이너의 프록시가 접근할 수 없다. Coolify의 Dockerfile 문서는 앱이 `0.0.0.0`에서 수신하도록 안내한다. `0.0.0.0`은 앱이 컨테이너의 모든 IPv4 인터페이스에서 수신한다는 의미이며, 그 설정만으로 서버 외부에 포트가 공개되는 것은 아니다. [공식 문서: Dockerfile](https://coolify.io/docs/applications/builds/dockerfile)

Ports Mappings는 서버 포트를 컨테이너 포트에 연결하는 별도 설정이다.

```text
설명용 포트 매핑: 18080:8080

클라이언트 -> 서버주소:18080 -> 컨테이너:8080
```

이 경로는 도메인을 보고 앱을 선택하는 HTTP 프록시 경로와 다르다. 공개 포트는 바인딩 주소와 방화벽 등에 따라 접근 범위가 정해진다. [Docker 공식 문서: Port publishing](https://docs.docker.com/engine/network/port-publishing/)

### Domains 필드의 포트 표기

Coolify의 Domains 설정에서 URL에 붙이는 포트는 내부 전달 대상 포트를 지정하는 용도로 사용된다. 예를 들어 공식 문서의 형식에 따라 다음처럼 설정하면 내부 8080 포트를 대상으로 지정한다.

```text
Coolify Domains 설정값
  https://api.example.com:8080

사용자가 브라우저에서 접속할 주소
  https://api.example.com
```

이것은 Coolify 설정값의 해석 규칙이다. 브라우저 주소에 직접 `:8080`을 붙이면 브라우저는 실제 외부 8080 포트로 접속을 시도한다. 두 경우를 구분해야 한다. 내부 포트 설정과 Domains 값이 같은 대상 포트를 나타내는지 확인한다. [공식 문서: Domains](https://coolify.io/docs/core/networking/domains)

## 5. HTTPS와 인증서

HTTPS는 HTTP 통신을 TLS로 보호하는 방식이다. TLS는 통신을 암호화하고 데이터 변조를 방지하며, 클라이언트는 인증서로 접속 대상의 신원을 검증한다. 인증서는 해당 호스트 이름에 유효하고 신뢰할 수 있어야 한다.

Coolify의 통합 프록시에서 `https://` 도메인을 설정하면 인증서 발급과 갱신을 자동화할 수 있다. 발급을 위해서는 도메인 제어 권한 검증이 성공해야 한다. 일반적인 공개 웹 구성에서는 올바른 DNS와 프록시까지의 접속 경로가 필요하다. 인증서 발급 방식에 따라 검증 조건이 달라지므로 와일드카드 인증서나 DNS 검증을 사용하는 구성은 별도로 확인한다. [공식 문서: Domains](https://coolify.io/docs/core/networking/domains)

### 암호화 구간은 연결별로 구분한다

프록시에서 TLS를 종료하고 앱에는 HTTP로 전달하는 구성은 다음과 같다.

```text
브라우저
  -- HTTPS/TLS --> 프록시
  -- 이 연결은 프록시에서 종료

프록시
  -- HTTP --> 앱 컨테이너
```

TLS 종료는 프록시가 암호화된 연결을 처리하고 복호화한다는 뜻이다. 프록시에서 앱으로 전달하는 연결은 별개의 연결이며, 그 구간도 암호화하려면 HTTPS 백엔드 등 별도 설정이 필요하다. 브라우저에서 HTTPS로 접속된다는 사실만으로 DB 연결까지 포함한 모든 내부 통신이 암호화되었다고 판단하지 않는다. [Traefik 공식 문서: HTTPS overview](https://doc.traefik.io/traefik/reference/routing-configuration/http/tls/overview/)

CDN이나 로드 밸런서가 앞에 있으면 브라우저에서 CDN, CDN에서 서버 프록시, 프록시에서 앱으로 이어지는 각 구간을 나눠 확인해야 한다.

## 6. DNS 설정과 Coolify 도메인 설정

두 설정은 서로 다른 역할을 한다.

| 설정 위치 | 역할 |
| --- | --- |
| DNS 제공 업체 | 도메인이 조회될 접속 주소 설정 |
| Coolify 리소스의 Domains | 해당 도메인의 요청을 전달할 앱 설정 |
| 서버 방화벽과 보안 그룹 | 필요한 접속 경로 허용 |
| 앱 실행 설정 | 내부 포트에서 실제 요청 수신 |

사용자 소유 도메인을 Coolify에 입력하는 것만으로 DNS 제공 업체의 레코드가 자동으로 만들어지는 것은 아니다. 두 설정을 각각 맞춰야 한다.

일반적인 구성 순서는 다음과 같다.

1. 리소스가 실행되는 서버와 외부 접속 경로를 확인한다.
2. DNS 제공 업체에서 해당 경로를 가리키는 레코드를 설정한다.
3. 리소스의 General 설정에서 Domains에 완전한 URL을 입력한다.
4. 앱의 내부 수신 포트와 저장한 설정을 확인한다.
5. 저장 후 재배포하여 프록시 설정을 적용한다.
6. 실제 도메인 접속, 인증서, 앱 응답을 확인한다.

Coolify의 Domains 공식 문서는 도메인 변경 후 재배포와 실제 접속 확인을 안내한다. 이 절차는 통합 프록시를 사용하는 경우이며, 사용자 정의 프록시에서는 전달 규칙과 인증서를 직접 관리한다. [공식 문서: Domains](https://coolify.io/docs/core/networking/domains)

## 7. DB 연결과 외부 접속은 별도 경로다

```text
사용자 요청
  -> 도메인
  -> HTTP 프록시
  -> Spring 앱

DB 조회
  -> Spring 앱
  -> DB 주소와 DB 포트
  -> MySQL
```

앱과 MySQL이 같은 사용자 정의 Docker 네트워크에 있다면 내부 이름과 포트로 연결할 수 있다. 이 연결을 위해 MySQL에 웹 도메인을 붙이거나 서버에 DB 포트를 공개할 필요는 없다.

반대로 웹 화면이 열린다고 DB 연결도 정상이라는 뜻은 아니다. 웹 요청의 전달과 DB 접속은 대상, 포트, 인증 방식이 다르다. DB가 외부 서버에 있으면 해당 서버까지의 네트워크 경로와 접근 정책이 필요하다. [공식 문서: Networking in Coolify](https://coolify.io/docs/core/networking-in-coolify)

## 8. 접속 문제를 확인하는 순서

증상만으로 원인을 단정하지 않고 요청 경로를 따라 확인한다.

| 단계 | 확인할 내용 |
| --- | --- |
| DNS | 도메인이 의도한 서버 또는 CDN 주소로 조회되는가? |
| 외부 연결 | 방화벽, 보안 그룹, 중간 장비가 필요한 포트의 연결을 허용하는가? |
| TLS | 접속한 호스트 이름에 유효한 인증서가 제공되는가? |
| 프록시 | 실행 중이며 해당 도메인의 전달 규칙이 있는가? |
| Docker 네트워크 | 프록시와 앱 사이에 통신 경로가 있는가? |
| 앱 포트 | 프록시 대상 포트와 앱의 실제 수신 포트가 일치하는가? |
| 앱 상태 | 준비 상태와 앱 로그, 실제 API 응답이 정상인가? |
| DB 등 의존 대상 | 내부 주소, 포트, 네트워크, 인증 설정이 올바른가? |

DNS는 서버 터미널에 접속하지 않아도 내 컴퓨터에서 조회할 수 있다. 다음 명령은 실제 도메인으로 바꿔 실행한다.

```shell
dig +short api.example.com A
dig +short api.example.com AAAA
```

조회 결과가 예상 주소와 다르면 DNS 설정과 캐시를 확인한다. 예상 주소가 나와도 이후 연결 단계의 성공까지 보장하지는 않는다. CDN을 사용하는 경우에는 CDN 주소가 나오는 것이 정상일 수 있다. [공식 문서: DNS](https://coolify.io/docs/core/networking/dns)

404나 502 같은 HTTP 상태 코드도 그 자체로 단일 원인을 확정하지는 않는다. 프록시가 반환했는지 앱이 반환했는지, 어느 로그에 요청이 남는지 함께 확인해야 한다. 서버 터미널을 사용할 수 없다면 웹 화면의 설정과 로그로 확인한 범위를 구분하고, 나머지 서버 측 상태는 인프라 담당자에게 확인한다.

## 9. 정리

DNS는 도메인의 접속 주소를 알려주고, 프록시는 도착한 요청을 알맞은 앱과 내부 포트로 전달한다. 앱은 Docker 네트워크에서 요청을 받아 처리하며, DB 연결은 별도의 경로를 사용한다.

Coolify의 도메인 설정과 DNS 레코드는 각각 관리해야 한다. HTTPS 역시 연결 구간별로 확인해야 하며, 외부 접속이 암호화되었다고 모든 내부 연결까지 암호화되는 것은 아니다.

도메인 접속이 실패하면 DNS부터 앱과 의존 대상까지 경로를 나누어 확인한다. 컨테이너 실행 여부와 실제 사용자 요청의 성공 여부를 함께 확인해야 전체 통신 상태를 이해할 수 있다.
