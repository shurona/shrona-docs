# Coolify의 리소스 구성

Coolify 화면의 Project, Environment, Resource는 배포 대상을 관리하는 구조다. Server와 Destination은 실제 실행 위치와 네트워크를 지정하는 데 사용한다. 이 두 관점을 구분하면 개발 환경과 운영 환경이 어떻게 배치되어 있는지 이해할 수 있다.

## 1. Project와 Environment

Project는 관련 리소스를 묶는 프로젝트 단위다. 그 안에 Environment를 두어 개발용, 운영용 등의 용도를 구분한다. Resource는 배포하고 관리하는 앱이나 DB 같은 대상이며, 프로젝트와 환경에 속한다. [공식 문서: What is Coolify](https://coolify.io/docs/core/what-is-coolify)

다음은 병원 서비스를 관리하는 설명용 구성이다.

```text
Project: hospital
  |
  +-- Environment: development
  |     +-- Spring 앱
  |     +-- 개발용 MySQL
  |
  +-- Environment: production
        +-- Spring 앱
        +-- 운영용 MySQL
```

이 구분은 실제 서버 개수를 뜻하지 않는다. 개발용과 운영용 앱을 같은 서버에 배치할 수도 있고, 서로 다른 서버에 배치할 수도 있다.

### Environment와 환경변수는 다르다

Environment는 리소스를 묶는 관리 단위다. 환경변수는 앱이 실행할 때 읽는 설정값이다.

Environment를 development라고 이름 붙이는 것만으로 Git 브랜치, Spring 프로필, DB 주소가 자동으로 개발용으로 바뀌지는 않는다. 실제 배포 소스와 실행 설정을 각각 지정해야 한다.

앱이 DB 주소 환경변수를 읽도록 구성되어 있고 그 값이 운영 DB를 가리킨다면, development에 속한 앱이어도 운영 DB로 연결을 시도한다. 연결 성공 여부는 네트워크와 인증 설정에도 달려 있다.

따라서 관리상 소속과 실제 실행 설정을 함께 확인해야 한다.

## 2. Resource의 종류

Coolify는 Application, Database, Service 같은 리소스를 관리한다. 각각은 배포와 설정을 다루는 방식이 다르다.

| 종류 | 역할 | 예시 |
| --- | --- | --- |
| Application | 소스 코드나 이미지로 앱 배포 | GitHub의 Spring Boot 앱 |
| Database | 지원하는 DB를 전용 설정으로 관리 | 독립적으로 생성한 MySQL |
| Service | Docker Compose 구성으로 소프트웨어 배포 | 앱과 DB를 함께 정의한 구성 |

Application은 Git 저장소, Dockerfile, Docker Compose 파일, 이미 만들어진 Docker 이미지 등을 사용할 수 있다. Database는 DB에 맞는 영속 저장 공간, 실행 제어, 백업 설정 등을 제공한다. [공식 문서: What is Coolify](https://coolify.io/docs/core/what-is-coolify)

### Service는 Compose 구성을 관리하는 단위다

Docker Compose는 컨테이너와 네트워크, 저장 공간 등의 실행 구성을 YAML 파일에 정의하는 도구다. Coolify의 Service는 준비된 템플릿이나 직접 작성한 Compose 정의를 사용한다.

```text
개별 리소스로 관리
  +-- Application: Spring 앱
  +-- Database: MySQL

Service로 관리
  +-- Service: Compose 구성
        +-- 앱 컨테이너
        +-- DB 컨테이너
```

Service 하나에 앱과 DB 등 여러 구성 요소가 들어갈 수 있다. 따라서 리소스 하나가 반드시 컨테이너 하나를 뜻하지는 않는다. Compose 정의는 의도한 구성을 보여주고, 실제로 몇 개가 실행 중인지는 실행 상태에서 확인한다.

Application도 Git 저장소의 Compose 파일을 사용할 수 있으므로, 컨테이너 개수만으로 Application과 Service를 구분해서는 안 된다. 소스 코드를 따라 배포할지, Coolify에 저장한 Compose 구성을 관리할지 등 배포 방식도 함께 봐야 한다. [공식 문서: Services](https://coolify.io/docs/services)

여기서 Service는 Spring 코드의 `@Service`나 서비스 사업 전체를 뜻하는 말이 아니라, Coolify의 리소스 종류 이름이다.

## 3. Server는 실제 실행 장소다

Server는 Docker와 컨테이너를 실행하는 컴퓨팅 자원이다. 물리 서버일 수도 있고 AWS EC2 같은 가상 서버 인스턴스일 수도 있다.

Service가 실행할 소프트웨어 구성이라면, Server는 그 구성을 실행하는 장소다. 하나의 서버에 여러 리소스를 배치할 수 있다.

```text
Server: 서버 A
  |
  +-- Docker
        +-- Application: Spring 앱
        +-- Database: MySQL
        +-- Service: 모니터링 구성
              +-- 모니터링 앱 컨테이너
              +-- 필요한 추가 컨테이너
```

Coolify는 연결된 서버에 작업을 지시하고, 해당 서버의 Docker가 컨테이너를 실행한다. 관리 서버와 앱 실행 서버가 같은 장비인지 여부는 배치 구성에 따라 달라진다. [공식 문서: How Coolify works](https://coolify.io/docs/core/how-coolify-works)

## 4. Destination은 서버의 Docker 네트워크를 나타낸다

Destination은 특정 서버의 Docker 네트워크를 나타내는 배포 대상이다. 하나의 Destination은 하나의 서버에 속하며, 서버 하나에 여러 Destination을 둘 수 있다.

```text
Server: 서버 A
  |
  +-- Destination: dev-destination
  |     Docker Network: dev-network
  |
  +-- Destination: prod-destination
        Docker Network: prod-network
```

이 구성은 서버 한 대 안의 네트워크를 나눈 것이다. Destination을 추가해도 서버가 추가되지는 않는다. [공식 문서: Destinations overview](https://coolify.io/docs/core/networking/destinations/overview)

### Destination 화면의 항목

| 항목 | 의미 |
| --- | --- |
| Name | Coolify 화면에서 구분하는 표시 이름 |
| Server IP | Destination이 속한 서버의 접속 주소 |
| Docker Network | 해당 서버에서 사용하는 Docker 네트워크 이름 |

Name과 Docker Network에 같은 문자열이 표시되어도 역할은 다르다. 표시 이름을 바꾸는 것은 Docker 네트워크 이름을 바꾸는 작업이 아니다. [공식 문서: Manage Destinations](https://coolify.io/docs/core/networking/destinations/manage)

### Compose 리소스의 네트워크

Compose 기반 Application과 Service는 기본적으로 리소스 자체의 네트워크를 사용하며, 선택한 Destination의 네트워크에 자동으로 참여하지 않는다. Destination 네트워크에도 연결하려면 `Connect To Predefined Network` 설정을 사용한다. [공식 문서: Destinations overview](https://coolify.io/docs/core/networking/destinations/overview)

따라서 Destination의 Resources 목록은 리소스의 배포 대상 설정을 확인하는 데 사용할 수 있지만, 모든 컨테이너의 실제 네트워크 연결 상태를 대신하지는 않는다.

Destination 하나를 확인했다는 사실과 서버에 Docker 네트워크가 하나만 존재한다는 주장은 다르다. Compose 등이 만든 별도의 네트워크가 있을 수 있다. 실제 통신 가능 여부는 컨테이너가 연결된 네트워크와 접속 경로를 기준으로 판단해야 한다.

## 5. 웹 화면에서 확인하는 방법

다음 경로는 공식 문서 기준이다. 설치된 버전과 계정 권한에 따라 메뉴 표시가 달라질 수 있다.

### Server 확인

```text
왼쪽 메뉴 Servers
  -> 서버 선택
  -> Configuration > General
```

서버 이름과 접속 주소, SSH 연결 설정 등을 확인한다. 서버 이름은 관리용 표시이므로 이름만으로 실제 장비의 위치나 사양을 추정하지 않는다. [공식 문서: Manage Server](https://coolify.io/docs/core/infrastructure/servers/manage-server)

### Destination 확인

```text
왼쪽 메뉴 Destinations
  -> Destination 선택
  -> General
```

Name, Server IP, Docker Network를 확인한다. Resources 목록에서는 해당 Destination을 사용하는 리소스를 살펴볼 수 있다. [공식 문서: Manage Destinations](https://coolify.io/docs/core/networking/destinations/manage)

## 6. 관리상 분리와 장애 영향은 다르다

Environment를 나누는 것은 개발용과 운영용 리소스를 관리상 구분하는 것이다. Destination으로 네트워크를 나누는 것은 통신 구성을 구분하는 것이다. 어느 쪽도 서버의 CPU, 메모리, 디스크까지 별도 장비로 분리하는 것은 아니다.

같은 서버에 개발용과 운영용 앱을 배치했다면 서버 자체가 멈출 때 둘 다 영향을 받는다. 개별 서비스 장애는 공유 자원과 의존 관계에 따라 영향 범위가 달라진다.

| 상황 | 영향 범위를 판단하는 기준 |
| --- | --- |
| 앱 프로세스 하나가 종료됨 | 다른 앱이 해당 앱에 의존하는지 |
| 한 앱이 서버 메모리나 디스크를 소진함 | 같은 서버의 다른 앱이 공유 자원 부족에 영향을 받는지 |
| 공통 DB나 프록시에 장애가 발생함 | 어떤 앱이 그 구성 요소를 사용하는지 |
| 서버 자체가 멈춤 | 그 서버에서 어떤 리소스가 실행 중인지 |

서비스를 따로 배포했다는 사실만으로 장애 영향이 완전히 분리되었다고 판단할 수 없다. 별도 서버에 배치하더라도 공통 DB나 네트워크 같은 의존 요소가 있으면 함께 영향을 받을 수 있다.

## 7. 정리

| 항목 | 답하는 질문 |
| --- | --- |
| Project | 어떤 프로젝트에 속하는가? |
| Environment | 개발용, 운영용 등 어떤 용도로 구분하는가? |
| Application / Database / Service | 무엇을 어떤 방식으로 배포하고 관리하는가? |
| Server | 실제로 어느 컴퓨팅 자원에서 실행하는가? |
| Destination | 어느 서버의 Docker 네트워크를 배포 대상으로 사용하는가? |

Coolify의 구성을 읽을 때는 관리상 소속, 실제 실행 설정, 실행 위치, 네트워크 연결을 구분해야 한다. 같은 Environment에 있다는 이유만으로 같은 네트워크라고 판단하거나, 다른 Environment에 있다는 이유만으로 장애 영향이 분리되었다고 판단해서는 안 된다.

리소스가 어디에 속하는지 확인한 뒤, 어떤 설정으로 어느 서버에서 실행되고 무엇과 연결되는지까지 확인해야 실제 구성을 이해할 수 있다.
