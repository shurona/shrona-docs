# Coolify의 역할과 전체 구조

Coolify에서 배포 버튼을 누르면 앱이 실행된다. 하지만 Coolify, 서버, Docker, 앱이 각각 어떤 역할을 하는지 구분하지 않으면 장애가 발생했을 때 어디를 확인해야 하는지 판단하기 어렵다.

이 글의 목표는 배포와 사용자 요청의 흐름을 구분하고, "배포 성공", "컨테이너 실행", "서비스 정상 동작"이 서로 다른 상태라는 것을 이해하는 것이다.

## 1. Coolify는 무엇을 하는 도구인가?

Coolify는 앱의 배포와 운영 작업을 관리하는 도구다. 웹 화면에서 소스 코드, 환경변수, 실행 포트 등을 설정하면 이를 바탕으로 서버에서 필요한 작업을 수행한다.

예를 들어 GitHub의 Spring Boot 코드를 배포하려면 코드를 가져오고, 빌드하고, 실행 환경을 설정하고, 새 버전을 실행해야 한다. Coolify는 이 과정을 자동화한다. 실제 앱의 요청을 처리하는 것은 Spring Boot이고, 컨테이너를 실행하는 것은 Docker다.

```text
Coolify : 배포 설정과 작업을 관리
서버    : CPU, 메모리, 디스크, 네트워크를 제공
Docker  : 컨테이너를 생성하고 실행
프록시  : 사용자 요청을 알맞은 앱에 전달
앱      : 서비스 기능을 실행
DB      : 앱이 사용하는 데이터를 저장
```

Coolify는 Docker를 대체하는 도구가 아니다. Docker 등을 활용해 배포와 운영을 관리한다. [공식 문서: How Coolify works](https://coolify.io/docs/core/how-coolify-works)

## 2. 구조를 이해하는 데 필요한 Docker 기초

### 이미지와 컨테이너

이미지는 앱을 실행하는 데 필요한 파일과 실행 설정을 담은 결과물이다. Dockerfile 등의 빌드 지시를 통해 이미지를 만들고, 그 이미지로 컨테이너를 생성한다. 이미 만들어진 이미지를 내려받아 사용할 수도 있다.

```text
소스 코드 + 빌드 지시
  -> 빌드
  -> 이미지
  -> 컨테이너 생성 및 실행
```

컨테이너는 이미지를 기반으로 만든 격리된 실행 환경이다. 실행 중에는 그 안에서 앱 프로세스가 동작한다. 별도의 운영체제를 통째로 실행하는 가상 머신과 달리, 컨테이너는 호스트의 커널을 공유한다.

이미지 하나로 여러 컨테이너를 만들 수 있지만, 배포를 여러 번 했다는 사실만으로 여러 컨테이너가 동시에 실행 중이라고 판단할 수는 없다.

### 포트

포트는 프로그램이 통신을 받는 번호다. 예를 들어 Spring Boot가 컨테이너 내부의 8080 포트에서 요청을 받을 수 있다.

Docker의 포트 매핑은 서버의 포트와 컨테이너의 포트를 연결하는 설정이다.

```text
예시: 서버 8081 포트를 컨테이너 8080 포트에 매핑

클라이언트 -> 서버:8081 -> 컨테이너:8080
```

이 숫자는 설명용 예시이며, 현재 서비스의 실제 설정을 뜻하지 않는다.

### 볼륨

볼륨은 컨테이너와 별도로 데이터를 보관하는 저장 공간이다. 컨테이너 내부 경로에 연결해서 사용한다. 이런 연결을 마운트라고 한다.

컨테이너를 단순히 종료하는 것만으로 내부 파일이 사라지지는 않는다. 하지만 컨테이너를 삭제하면 그 컨테이너의 쓰기 가능한 내부 파일 영역도 사라진다. 새 컨테이너에서도 DB 데이터를 사용하려면 볼륨 같은 별도의 영속 저장 공간이 필요하다.

```text
기존 MySQL 컨테이너 -> 데이터 볼륨
기존 컨테이너 삭제
새 MySQL 컨테이너   -> 기존 데이터 볼륨 연결
```

볼륨도 삭제하거나 디스크가 손상되면 데이터를 잃을 수 있으므로, 볼륨과 백업은 같은 개념이 아니다.

## 3. 배포 흐름과 사용자 요청 흐름

### 배포와 관리

아래는 Git 소스 코드로 이미지를 빌드하는 배포의 개념적인 흐름이다. 실제 단계와 순서는 빌드 방식에 따라 달라진다.

```text
관리자가 Coolify에서 배포 실행
  -> Coolify가 배포 설정을 확인
  -> 대상 서버에 SSH로 작업 지시
  -> 코드 가져오기 및 이미지 빌드
  -> 환경변수, 네트워크, 저장 공간 등의 설정 적용
  -> 새 앱 컨테이너 실행 및 요청 전달 설정
```

SSH는 원격 서버에 접속하고 명령을 실행할 수 있게 해주는 통신 방식이다. 이미 만들어진 이미지를 배포한다면 코드 빌드 대신 이미지를 내려받는 과정이 사용될 수 있다. [공식 문서: How Coolify works](https://coolify.io/docs/core/how-coolify-works)

### 사용자의 서비스 이용

도메인과 HTTP 프록시를 사용하는 일반적인 구성은 다음과 같다.

```text
브라우저가 앱 도메인의 주소를 DNS로 조회
  -> 해당 서버에 요청
  -> 프록시
  -> Spring 앱 컨테이너
  -> 필요한 경우 MySQL 조회
  -> 결과 응답
```

DNS는 도메인 이름에 해당하는 IP 주소 등의 정보를 조회하는 시스템이다. 프록시는 요청의 도메인과 경로 등을 보고 알맞은 앱으로 전달하는 중간 프로그램이다. 예를 들어 api.example.com으로 들어온 요청을 Spring 앱으로 보낸다.

사용자 요청은 Coolify 관리 화면을 통과하지 않는다. 프록시가 앱으로 직접 전달한다. 또한 앱과 DB가 공유하는 Docker 네트워크에서 통신할 경우에는 외부 도메인이나 서버 포트 매핑 없이 내부 이름과 포트로 연결할 수 있다. 외부 DB를 사용하는 경우에는 그 DB까지의 별도 네트워크 연결이 필요하다. [공식 문서: Networking in Coolify](https://coolify.io/docs/core/networking-in-coolify)

## 4. Coolify와 앱은 어디에 배치되는가?

### 서버 하나에 함께 배치

```text
서버 A
  - Docker
    - Coolify 관리 구성 요소
    - 프록시
    - Spring 앱 컨테이너
    - MySQL 컨테이너 (이 서버에 DB를 배치한 경우)
```

같은 서버의 자원을 공유하는 구성이다. 관리 화면에만 문제가 생기면 앱은 계속 동작할 수 있지만, 서버 자체가 멈추면 둘 다 영향을 받을 수 있다.

### 관리 서버와 앱 서버를 분리

```text
서버 A                         서버 B
  Coolify                      Docker
    |                            - 프록시
    +------ SSH로 관리 --------> - Spring 앱 컨테이너

사용자 ----------------------> 서버 B의 프록시
                                -> Spring 앱
```

서버 A만 사용할 수 없게 되었다면, 서버 B와 DB 등 서비스에 필요한 구성 요소가 정상이라는 조건에서 기존 앱은 계속 동작할 수 있다. 다만 서버 A의 Coolify를 통한 새 배포와 설정 변경은 할 수 없다. [공식 문서: How Coolify works](https://coolify.io/docs/core/how-coolify-works)

## 5. Coolify 관리용 DB와 서비스용 DB

두 DB는 저장하는 정보와 역할이 다르다.

```text
Coolify    -> 관리용 DB : 프로젝트 설정, 배포 관련 상태 등
Spring 앱  -> 서비스 DB : 회원 정보와 서비스 데이터 등
```

따라서 Coolify 화면이 열린다고 해서 Spring 앱의 MySQL 연결도 정상이라고 판단할 수 없다. 반대로 앱의 DB 연결 오류만으로 Coolify 관리용 DB에도 문제가 있다고 판단할 수 없다.

## 6. 배포 성공과 서비스 정상 동작은 다르다

다음 네 가지를 구분해서 확인한다.

| 확인 대상 | 알 수 있는 내용 | 이것만으로 확정할 수 없는 내용 |
| --- | --- | --- |
| 배포 기록의 Success | 해당 배포 작업이 성공으로 기록됨 | 현재 서비스의 모든 기능이 정상인지 |
| 컨테이너 실행 상태 | 컨테이너의 주 프로세스가 실행 중임 | 요청 처리와 DB 연결이 정상인지 |
| 앱 로그 | 기록된 실행 상황과 오류 | 아직 실행하지 않은 기능까지 정상인지 |
| 실제 API 요청 | 테스트한 기능의 응답과 동작 | 테스트하지 않은 모든 기능의 정상 여부 |

배포 기록에 Success가 5개 있다고 해서 현재 앱 컨테이너가 5개 실행 중인 것은 아니다. 배포 기록은 과거 작업의 이력이고, 현재 실행 개수는 별도로 확인해야 한다.

컨테이너가 실행 중이어도 프록시가 멈추면 사용자의 요청이 앱에 도달하지 못할 수 있다. 앱이 요청을 받더라도 DB에 연결하지 못하면 DB가 필요한 기능을 처리하지 못할 수 있다.

로그에 오류가 없다는 것만으로도 충분하지 않다. 특정 기능을 호출하기 전까지 오류가 나타나지 않을 수 있으므로 실제로 DB를 사용하는 API도 확인해야 한다.

## 7. 정리

Coolify는 배포 설정과 운영 작업을 관리하고, Docker는 서버에서 컨테이너를 실행한다. 도메인과 HTTP 프록시를 사용하는 구성에서 사용자 요청은 프록시를 거쳐 앱으로 전달되며, Coolify 관리 화면을 통과하지 않는다.

관리 기능과 서비스 실행 경로가 구분되므로 Coolify 관리 화면의 장애가 반드시 앱의 중단을 의미하지는 않는다. 다만 같은 서버의 자원을 공유하거나 서비스에 필요한 프록시, 네트워크, DB에 문제가 생기면 앱 이용에도 영향을 줄 수 있다.

서비스 상태를 판단할 때는 배포 성공, 컨테이너 실행, 실제 기능의 정상 동작을 구분해야 한다. 배포 기록과 실행 상태를 확인하고, 앱 로그와 실제 API 응답으로 필요한 기능이 정상 동작하는지 확인한다.
