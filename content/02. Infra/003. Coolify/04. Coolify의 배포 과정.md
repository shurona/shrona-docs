# Coolify의 배포 과정

GitHub에 코드를 올리는 것과 실행 중인 앱에 그 코드가 반영되는 것은 별개의 과정이다. Coolify는 배포 요청을 받아 코드와 이미지를 준비하고, 실행 설정을 적용한 컨테이너로 앱을 갱신한다.

이 글은 GitHub 저장소의 Dockerfile을 사용하는 Application 배포를 중심으로 설명한다. 특정 서버의 설정이나 장애 원인을 추정하지 않고, 공식 문서에서 확인한 동작과 적용 조건을 다룬다. 화면과 세부 동작은 설치 버전에 따라 확인해야 한다.

## 1. 전체 배포 흐름

```text
배포 요청
  -> 배포 작업 대기 및 시작
  -> 대상 저장소와 코드 버전 확인
  -> 이미지 빌드 또는 재사용
  -> 환경변수, 네트워크, 저장 공간 등 실행 설정 준비
  -> 구성에 맞는 방식으로 컨테이너 교체
  -> 배포 결과와 실제 서비스 응답 확인
```

배포는 큐에 등록된 작업으로 처리된다. 요청 직후 대기 상태일 수 있으며, 실행 차례가 되면 작업이 진행된다. Coolify가 작업을 조정하고 실제 이미지 빌드와 컨테이너 실행은 Docker가 수행한다. [공식 문서: Build and deployment model](https://coolify.io/docs/core/build-deployment-model)

헬스체크와 기존 컨테이너 중지 시점은 모든 배포에서 동일하지 않다. 새 컨테이너를 먼저 실행할 수 있는지, 헬스체크가 설정되어 있는지에 따라 교체 과정이 달라진다.

## 2. 배포할 코드 선택

### 저장소, 브랜치, 커밋

| 항목 | 역할 |
| --- | --- |
| Repository | 코드를 가져올 저장소 |
| Branch | 배포 대상으로 선택한 개발 흐름 |
| Commit | 배포할 정확한 코드 상태를 식별하는 버전 |

브랜치는 새 커밋이 추가되면 가리키는 코드가 바뀐다. 커밋 ID는 특정 코드 상태를 식별한다. 따라서 배포 버전을 확인할 때는 브랜치 이름뿐 아니라 실제 커밋도 확인한다.

Application이 dev 브랜치를 대상으로 설정되어 있다면, feature/login에만 있는 변경 사항은 dev의 코드에 포함되지 않는다. 해당 변경을 dev에 합치거나 배포 대상을 변경해야 한다.

Git 기반 Application은 저장소 주소와 브랜치, 필요한 접근 권한을 설정한다. 비공개 저장소는 GitHub App이나 배포 키 등으로 접근 권한을 제공해야 한다. [공식 문서: Application sources](https://coolify.io/docs/applications/sources/overview)

### 배포 대상과 배포 시작 계기

배포 대상은 어떤 코드를 실행할지에 대한 설정이다. 배포 시작 계기는 언제 그 작업을 수행할지에 대한 설정이다.

```text
배포 대상
  -> 저장소, 브랜치, 커밋

배포 시작 계기
  -> 웹 화면에서 수동 실행
  -> Git 이벤트에 의한 자동 배포
  -> 외부 자동화의 배포 요청
```

자동 배포가 구성되어 있다면 선택한 브랜치의 변경 이벤트로 배포를 시작할 수 있다. 코드 업로드 자체가 실행 중인 컨테이너의 파일을 수정하는 것은 아니다. [공식 문서: Automatic deployments](https://coolify.io/docs/applications/deployments/automatic-deployments)

## 3. Dockerfile과 빌드 컨텍스트

Dockerfile은 이미지를 만드는 작업 지시서다. 빌드 컨텍스트는 빌드 과정에 제공하는 파일의 범위다. 일반적인 `COPY`는 컨텍스트에 포함된 파일을 복사하며, `.dockerignore`로 제외된 파일은 일반적인 복사 대상에서 빠진다. [Docker 공식 문서: Build context](https://docs.docker.com/build/concepts/context/)

```text
설명용 저장소 구조
  +-- Dockerfile
  +-- build.gradle
  +-- src/
  +-- README.md
```

이 저장소의 루트를 컨텍스트로 사용하면 Dockerfile에서 build.gradle과 src의 파일을 사용할 수 있다. 컨텍스트에 파일이 들어 있다는 사실만으로 최종 이미지에 자동 포함되는 것은 아니다. Dockerfile의 복사와 빌드 지시에 따라 이미지 내용이 결정된다.

Coolify의 Dockerfile 방식에서는 다음 설정을 구분한다.

| 설정 | 의미 |
| --- | --- |
| Base Directory | 저장소에서 빌드 컨텍스트로 사용할 디렉터리 |
| Dockerfile Location | Base Directory를 기준으로 한 Dockerfile 경로 |

Dockerfile이 저장소에 있더라도 경로나 컨텍스트가 맞지 않으면 필요한 파일을 찾지 못할 수 있다. [공식 문서: Dockerfile](https://coolify.io/docs/applications/builds/dockerfile)

## 4. Spring 앱의 JAR와 이미지 생성

JAR는 Java 앱을 배포할 때 사용하는 패키지 파일이다. 실행 가능한 Spring Boot JAR에는 빌드 시점의 앱 코드와 실행에 필요한 구성이 담긴다.

### 미리 만든 JAR를 이미지에 넣는 방식

```text
소스 코드
  -> 로컬 또는 CI에서 JAR 생성
  -> Dockerfile에서 JAR 복사
  -> 이미지 생성
```

CI는 코드 변경 후 빌드와 테스트 등을 자동으로 실행하는 환경을 말한다. 이 방식에서는 새 소스를 반영한 JAR가 Docker 빌드 전에 준비되어 있어야 한다.

Dockerfile이 기존 app.jar만 복사한다면 Java 소스를 수정해도 그 JAR의 내용이 자동으로 바뀌지는 않는다. 이미지를 다시 만들어도 오래된 JAR를 복사했다면 새 코드가 반영되지 않는다.

### Docker 빌드 안에서 JAR를 만드는 방식

```text
Docker 이미지 빌드
  -> 소스와 빌드 설정 복사
  -> Gradle 또는 Maven으로 JAR 생성
  -> 생성된 JAR를 최종 이미지에 포함
```

멀티 스테이지 빌드는 Dockerfile에서 여러 빌드 단계를 정의하고, 앞 단계의 결과물을 뒤 단계로 복사하는 방식이다. 빌드 단계에서는 JDK와 빌드 도구를 사용하고, 최종 이미지에는 Java 실행 환경과 JAR만 남기는 식으로 구성할 수 있다. [Docker 공식 문서: Multi-stage builds](https://docs.docker.com/build/building/multi-stage/)

### 이미지 재사용과 빌드 캐시

배포할 때마다 모든 빌드 작업을 처음부터 수행하는 것은 아니다. Coolify는 대상 커밋의 이미지가 이미 있고 빌드 설정이 바뀌지 않은 경우 그 이미지를 재사용할 수 있다. 이는 Docker 빌드가 실행되면서 기존 단계의 캐시를 사용하는 것과 구분된다. [공식 문서: Build and deployment model](https://coolify.io/docs/core/build-deployment-model)

```text
이미지 재사용
  -> 이미 준비된 이미지를 사용

빌드 캐시 사용
  -> 이미지 빌드를 수행하되 재사용 가능한 단계의 결과를 활용
```

이미지 빌드 성공은 앱 실행 성공을 뜻하지 않는다. 앱 파일을 이미지에 담는 과정이 성공했더라도 실행 설정이 잘못되면 시작이나 요청 처리에 실패할 수 있다.

## 5. 실행 설정과 컨테이너 시작

이미지가 준비되면 환경변수, 네트워크, 영속 저장 공간 등의 설정을 적용해 컨테이너를 생성한다. Dockerfile 방식에서도 이 실행 설정이 필요하다. [공식 문서: Dockerfile](https://coolify.io/docs/applications/builds/dockerfile)

```text
이미지
  + 실행 환경변수
  + 네트워크와 포트 설정
  + 볼륨 등의 저장 공간 연결
  + 실행 명령
    -> 컨테이너 생성 및 시작
    -> Spring 초기화
    -> 요청 처리 준비
```

DB 주소를 환경변수에서 읽도록 구성한 앱이라면 해당 값이 올바르게 전달되어야 한다. 값이 누락되었고 기본값이나 다른 설정에도 주소가 없다면 의도한 DB에 연결할 수 없다. 앱이 시작 단계에서 실패할지, DB를 사용하는 요청에서 실패할지는 초기화 방식에 따라 다르다.

컨테이너의 실행 상태와 앱의 준비 상태도 구분한다. Java 프로세스가 실행 중이어도 Spring 초기화가 끝나기 전에는 요청을 처리하지 못할 수 있다.

또한 프록시가 접근할 내부 포트와 앱의 실제 수신 포트가 일치해야 한다. 앱이 컨테이너의 루프백 주소에만 바인딩되어 있으면 다른 컨테이너의 프록시가 접근하지 못한다. Coolify의 Dockerfile 문서는 앱이 `0.0.0.0`에서 요청을 받도록 안내한다. [공식 문서: Dockerfile](https://coolify.io/docs/applications/builds/dockerfile)

## 6. 헬스체크로 확인하는 것

헬스체크는 설정한 요청이나 명령을 주기적으로 실행해 컨테이너의 상태를 판단하는 검사다. Coolify에서는 선택 설정이며, 없으면 앱의 요청 처리 준비가 완료되었다는 검사 결과도 없다.

| 정의 위치 | 사용 방식 |
| --- | --- |
| Coolify의 Configuration > Healthcheck | 이미지 정의를 바꾸지 않고 검사 설정 |
| Dockerfile의 HEALTHCHECK | 이미지에 검사 명령 포함 |
| Compose의 healthcheck | Compose 구성 요소별 검사 설정 |

일반 Dockerfile Application에서는 이미지에 `HEALTHCHECK`가 있으면 Coolify가 이를 사용하며, 화면에서 설정한 검사를 추가하지 않는다. Compose Application은 일반 Application의 Healthcheck 화면 대신 Compose 또는 이미지에 검사를 정의한다. [공식 문서: Health checks](https://coolify.io/docs/applications/configuration/health-checks)

HTTP 헬스체크를 Coolify에서 설정한 경우 검사는 앱 컨테이너 내부에서 수행되며, 최종 이미지에 curl 또는 wget이 필요하다. 검사 주소와 포트도 컨테이너 내부 기준이다. 시작에 시간이 걸리는 앱은 초기화 시간을 고려한 검사 간격과 시작 유예 시간을 설정해야 한다.

헬스체크가 검사하지 않는 기능까지 정상이라고 보장할 수는 없다. 예를 들어 DB를 확인하지 않고 항상 성공 응답을 반환하는 엔드포인트는 DB 연결 장애를 감지하지 못한다. 검사 목적은 실제 요청을 받을 준비 상태를 반영하도록 정해야 한다.

Traefik을 사용하는 Coolify 프록시는 헬스체크가 활성화된 경우 비정상 컨테이너를 요청 전달 대상에서 제외한다. 이 동작을 다른 프록시에도 그대로 일반화하지 않는다. [공식 문서: Health checks](https://coolify.io/docs/applications/configuration/health-checks)

## 7. 새 컨테이너로 교체하는 방식

### 롤링 업데이트

롤링 업데이트는 기존 컨테이너를 유지한 채 새 컨테이너를 시작하는 방식이다. 두 컨테이너가 동시에 실행될 수 있는 구성이어야 한다.

```text
기존 컨테이너가 실행 중인 상태
  -> 새 컨테이너 시작
  -> 설정된 헬스체크로 준비 상태 확인
  -> 준비된 새 컨테이너를 남기고 기존 컨테이너 중지 및 제거
```

검사에 실패하면 새 컨테이너를 제거하고 기존 컨테이너를 유지한다. 헬스체크가 없으면 시작한 컨테이너를 준비된 것으로 취급하므로 앱 초기화 완료를 검증한 것은 아니다. [공식 문서: Rolling updates](https://coolify.io/docs/applications/deployments/rolling-updates)

### 기존 컨테이너를 먼저 중지하는 방식

서버에 고정 포트를 공개했거나 같은 컨테이너 이름 또는 고정 IP를 사용하면 두 컨테이너를 동시에 실행하기 어렵다. 이런 설정에서는 기존 것을 먼저 중지하고 새 것을 시작한다. 공식 문서에서는 PR 미리보기 배포도 롤링 업데이트 제외 조건으로 설명한다.

이 방식은 새 앱이 시작하는 동안 중단 시간이 발생할 수 있으며, 롤링 업데이트의 기존 컨테이너 유지 동작을 그대로 기대해서는 안 된다. Compose 배포 역시 Coolify의 Application 수준 롤링 업데이트와는 다른 경로를 사용한다. [공식 문서: Rolling updates](https://coolify.io/docs/applications/deployments/rolling-updates)

### 무중단은 별도로 확인해야 한다

롤링 업데이트를 사용해도 무중단을 자동으로 보장하지는 않는다. 앱은 준비 상태를 정확히 알리고, 종료 시 처리 중인 요청을 정리해야 한다. 또한 두 버전이 잠시 함께 사용하는 DB나 공유 데이터가 양쪽 버전과 호환되어야 한다. 실제 요청이 전환 중에도 성공하는지 확인해야 무중단 여부를 판단할 수 있다. [공식 문서: Rolling updates](https://coolify.io/docs/applications/deployments/rolling-updates)

## 8. Deploy, Redeploy, Restart의 구분

| 작업 | 공식 문서에서 설명하는 동작 |
| --- | --- |
| Deploy | 설정한 앱의 첫 배포 시작 |
| Redeploy | 기존 앱에 일반 배포 흐름을 다시 실행 |
| Coolify의 Restart | 배포 큐를 통해 실행 구성을 다시 생성 |
| Force deploy (without cache) | Coolify가 생성하는 소스 빌드에서 캐시를 사용하지 않고 빌드 |

Coolify의 Restart는 Docker CLI의 `docker restart`와 같은 의미로 보면 안 된다. 소스 기반 경로는 가능한 경우 이미지를 재사용하지만 필요하면 빌드할 수 있다. Docker Image 방식은 저장된 이미지 참조를 다시 가져온다. [공식 문서: Deploy applications](https://coolify.io/docs/applications/deployments/overview)

기존 컨테이너를 단순 재시작하면 생성 당시 설정을 사용한다는 설명은 Docker의 컨테이너 재시작에 해당한다. Coolify 버튼의 동작은 해당 도구의 배포 흐름을 기준으로 이해해야 한다.

## 9. 배포 로그와 앱 로그

| 로그 | 주요 확인 대상 | 예시 |
| --- | --- | --- |
| 배포 로그 | 코드와 이미지 준비, 컨테이너 교체 과정 | 코드 가져오기 실패, 컴파일 오류, 교체 실패 |
| 앱 로그 | 앱 프로세스 내부의 초기화와 요청 처리 | Spring 시작 오류, DB 연결 예외, API 처리 오류 |

Application의 Deployments에서 배포 작업의 상태와 로그를 확인하고, 실행 중인 앱의 동작은 Logs에서 확인한다. [공식 문서: Build and deployment model](https://coolify.io/docs/core/build-deployment-model)

두 로그의 내용이 완전히 분리되는 것은 아니다. 배포 중 앱 시작이나 헬스체크가 실패하면 배포 로그에도 관련 내용이 나타날 수 있다. 먼저 실패한 단계를 구분한 뒤 그 원인을 설명하는 로그를 확인한다.

소스 빌드가 실패하면 일반적인 교체 흐름에서는 기존 앱을 교체하지 않는다. 반면 새 컨테이너를 실행한 뒤 실패했을 때의 영향은 교체 방식에 따라 달라진다. 따라서 실패 상태만 보고 기존 버전이 유지되었다고 단정하지 않는다. [공식 문서: Build and deployment model](https://coolify.io/docs/core/build-deployment-model)

## 10. 정리

Coolify 배포는 코드 선택, 이미지 준비, 실행 설정 적용, 컨테이너 교체를 연결하는 과정이다. Dockerfile은 이미지 생성 방법을 정의하고, 실제 실행에는 환경변수와 네트워크, 저장 공간 등의 설정이 함께 필요하다.

빌드 성공, 컨테이너 실행, 헬스체크 통과, 실제 기능의 정상 동작은 서로 다른 확인 단계다. 헬스체크는 정의한 검사만 검증하며, 컨테이너 교체 방식도 설정에 따라 달라진다.

배포를 확인할 때는 실제 커밋, 이미지 준비 결과, 교체 방식, 앱 로그와 최종 응답을 연결해서 살펴본다. 이 흐름을 구분하면 어떤 단계에서 문제가 발생했는지 판단할 수 있다.
