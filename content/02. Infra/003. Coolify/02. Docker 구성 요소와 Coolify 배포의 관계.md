# Docker 구성 요소와 Coolify 배포의 관계

Coolify의 배포 설정을 이해하려면 Docker의 이미지, 컨테이너, 환경변수, 네트워크, 볼륨이 각각 무엇을 담당하는지 알아야 한다. 코드를 바꾸는 작업, 실행 설정을 바꾸는 작업, 데이터를 유지하는 작업은 서로 다르기 때문이다.

이 글은 앱 코드가 이미지에 포함되는 일반적인 배포를 기준으로 설명한다. 실행 중인 컨테이너에 개발용 소스 폴더를 직접 연결하는 구성은 다루지 않는다.

## 1. 이미지와 컨테이너

### 이미지는 실행에 필요한 파일과 설정을 담는다

이미지는 컨테이너를 만드는 기반이다. 앱 실행 파일, 필요한 라이브러리, 실행 환경과 기본 설정 등을 담는다. Spring Boot 앱이라면 JAR 파일과 Java 실행 환경을 포함하도록 구성할 수 있다.

이미지 자체가 실행 중인 앱은 아니다. 이미지를 기반으로 컨테이너를 만들고 그 안에서 앱 프로세스를 실행한다. 하나의 이미지로 여러 컨테이너를 만들 수도 있다.

```text
소스 코드와 빌드 설정
  -> 앱 빌드 및 이미지 생성
  -> 이미지로 컨테이너 생성
  -> 컨테이너 안에서 앱 실행
```

이미지 내용은 생성 후 직접 바꾸는 것이 아니라, 변경된 내용을 담은 새 이미지를 만들어 갱신한다. 이미지 이름이나 태그가 같아도 그 이름이 가리키는 실제 이미지가 새 버전으로 바뀔 수 있다. [Docker 공식 문서: What is an image?](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/)

### GitHub 코드 변경과 배포는 별개의 과정이다

GitHub에 새 코드를 올려도 실행 중인 컨테이너의 파일이 자동으로 바뀌지는 않는다. 기존 컨테이너는 자신을 생성할 때 사용한 이미지의 코드를 실행한다.

```text
기존 코드 -> 이미지 v1 -> 기존 컨테이너 실행

새 코드 업로드
  -> 새 코드로 이미지 v2 빌드
  -> 이미지 v2로 새 컨테이너 실행
  -> 새 버전으로 서비스 전환
```

자동 배포가 설정되어 있다면 코드 업로드가 배포를 시작할 수 있다. 이것도 코드가 실시간으로 동기화되는 것이 아니라, 업로드를 계기로 새 배포가 진행되는 것이다.

Coolify는 소스로 이미지를 빌드하는 작업을 관리하거나, 이미 만들어진 이미지를 가져와 배포할 수 있다. 따라서 사용자가 항상 별도로 이미지를 빌드해서 전달해야 하는 것은 아니다. [Coolify 공식 문서: How Coolify works](https://coolify.io/docs/core/how-coolify-works)

기존 컨테이너를 단순히 재시작하는 것은 새 이미지로 교체하는 작업이 아니다. 재시작만으로 새 코드가 반영되지는 않는다.

## 2. 환경변수

### 같은 이미지에 서로 다른 실행 설정을 전달한다

환경변수는 프로세스가 실행 환경에서 읽을 수 있는 이름과 값의 쌍이다. 앱이 환경변수를 읽도록 구성되어 있으면 DB 주소 같은 설정을 코드와 분리할 수 있다.

각 컨테이너는 자신에게 전달된 환경변수를 가진다. 같은 이미지로 만든 컨테이너라도 서로 다른 값을 전달하면 다른 설정으로 앱을 실행할 수 있다.

```text
같은 앱 이미지
  +-> 개발 컨테이너 + 개발 DB 주소 -> 개발 DB 연결
  +-> 운영 컨테이너 + 운영 DB 주소 -> 운영 DB 연결
```

환경변수 이름을 임의로 정해서 전달한다고 앱이 자동으로 사용하는 것은 아니다. 앱이나 프레임워크가 해당 이름을 읽고 실제 설정에 적용하도록 구성되어 있어야 한다.

Docker CLI에서는 컨테이너 생성 시 `docker run`의 `--env` 또는 `--env-file` 옵션으로 값을 전달할 수 있다. 이미지에 설정된 기본 환경변수도 실행 시 전달한 값으로 재정의할 수 있다. [Docker 공식 문서: Running containers](https://docs.docker.com/engine/containers/run/)

### 실행 설정 변경에는 항상 새 이미지가 필요한 것은 아니다

앱이 DB 주소를 실행 시 환경변수로 읽는다면, DB 주소만 바꾸기 위해 이미지를 다시 빌드할 필요는 없다. 기존 이미지에 변경된 환경변수를 전달해서 새 컨테이너를 생성하면 된다.

반면 DB 주소가 코드나 이미지에 포함된 설정 파일에 고정되어 있다면, 그 내용을 수정한 새 이미지가 필요하다.

| 변경 대상 | 필요한 작업 |
| --- | --- |
| 이미지에 포함되는 앱 코드 | 새 이미지 빌드 후 컨테이너 교체 |
| 앱이 실행 시 읽는 환경변수 | 기존 이미지에 새 값을 전달해 컨테이너 생성 |

설정 화면이나 외부 환경변수 파일을 수정하는 것만으로 기존 컨테이너의 환경변수가 자동 갱신되지는 않는다. 단순 재시작은 생성 당시의 컨테이너 설정을 사용한다. 여기서 말하는 재시작은 Docker의 기존 컨테이너 재시작이며, 관리 도구가 제공하는 버튼의 내부 동작과는 구분한다.

### 빌드 과정에서도 변수를 사용할 수 있다

Dockerfile의 `ARG`는 빌드 과정에서 사용할 값을 받는다. `docker build --build-arg`로 값을 전달할 수 있으며, 컨테이너의 실행 환경변수로 자동 전달되지는 않는다.

Dockerfile의 `ENV`는 해당 빌드 단계의 환경변수를 설정한다. 최종 이미지에 포함된 `ENV` 설정은 그 이미지로 생성하는 컨테이너의 기본 환경변수로도 사용된다.

따라서 변수 변경에 재빌드가 필요한지는 그 값이 빌드 결과에 반영되는지, 실행할 때 읽히는지에 따라 판단해야 한다. 빌드에 필요한 비밀 값은 이미지나 메타데이터에 남을 수 있는 `ARG`나 `ENV` 대신 Docker의 빌드용 secret mount를 사용한다. [Docker 공식 문서: Build variables](https://docs.docker.com/build/building/variables/)

## 3. 네트워크와 포트

### 컨테이너의 localhost는 자기 자신이다

별도의 bridge 네트워크 공간을 사용하는 컨테이너에서 `localhost`는 그 컨테이너 자신을 가리킨다. 서버 호스트나 다른 컨테이너를 가리키지 않는다.

따라서 Spring 앱과 MySQL을 별도 컨테이너로 실행했다면, Spring에서 `localhost:3306`으로 접속해도 MySQL 컨테이너로 요청이 전달되지 않는다. 접속 가능한 DB의 이름이나 주소를 사용해야 한다.

### 사용자 정의 bridge에서 이름으로 연결한다

Docker의 기본 `bridge` 네트워크는 컨테이너 이름의 자동 DNS 조회를 제공하지 않는다. 사용자 정의 bridge에서는 같은 네트워크에 연결된 컨테이너를 이름이나 네트워크 별칭으로 찾을 수 있다.

이름을 이용하면 접속 설정에 컨테이너 IP를 직접 적지 않아도 된다. 네트워크 이름은 컨테이너들을 연결하는 공간의 이름이고, 컨테이너 이름이나 별칭은 그 안에서 접속 대상을 찾는 데 사용한다.

서로 다른 bridge 네트워크에만 연결된 컨테이너끼리는 기본적으로 직접 통신할 수 없다. 연결이 필요하면 공통 네트워크에 연결하거나, 접근 가능한 서버의 공개 포트를 사용하는 등의 경로를 구성해야 한다. [Docker 공식 문서: Bridge network driver](https://docs.docker.com/engine/network/drivers/bridge/)

### 내부 통신과 포트 공개

컨테이너 내부 포트는 앱이 연결을 받는 포트다. 포트 공개는 서버의 특정 포트에 들어온 연결을 컨테이너 포트로 전달하도록 설정하는 것이다.

```text
포트 매핑 형식: 서버 포트:컨테이너 포트

서버의 공개 포트
  -> 매핑된 컨테이너 포트
  -> 해당 포트에서 연결을 받는 앱
```

같은 사용자 정의 bridge의 컨테이너끼리는 대상 컨테이너의 이름과 내부 포트로 통신할 수 있다. 이 통신만을 위해 서버에 포트를 공개할 필요는 없다. 앱이 네트워크로 연결을 받을 수 있도록 설정되어 있어야 하며, DB 계정과 인증 설정도 올바르게 구성해야 한다. [Docker 공식 문서: Bridge network driver](https://docs.docker.com/engine/network/drivers/bridge/)

Coolify에서 도메인과 HTTP 프록시를 사용하는 앱은 프록시가 요청을 앱의 내부 포트로 전달한다. 앱과 DB 사이의 통신 경로는 이 사용자 HTTP 요청 경로와 별도로 구성된다. [Coolify 공식 문서: Networking in Coolify](https://coolify.io/docs/core/networking-in-coolify)

## 4. 볼륨

### 컨테이너와 데이터의 수명을 분리한다

컨테이너에는 실행 중 파일을 기록할 수 있는 쓰기 영역이 있다. 이 영역의 파일은 컨테이너를 종료해도 남지만, 컨테이너를 삭제하면 함께 제거된다.

볼륨은 컨테이너의 쓰기 영역과 별도로 Docker가 관리하는 저장 공간이다. 컨테이너 내부의 경로에 볼륨을 마운트하면 앱은 그 경로를 통해 볼륨에 데이터를 읽고 쓸 수 있다. 마운트는 저장 공간을 특정 경로에 연결하는 작업이다.

DB 데이터처럼 컨테이너를 교체해도 유지해야 하는 파일은 영속 저장 공간에 보관해야 한다. 다만 볼륨을 연결했다는 사실만으로 모든 파일이 보존되는 것은 아니다. 실제 데이터가 기록되는 경로에 연결해야 한다. [Docker 공식 문서: Volumes](https://docs.docker.com/engine/storage/volumes/)

### 기존 볼륨을 새 컨테이너에 연결한다

```text
기존 DB 컨테이너 -> 데이터 볼륨에 기록
기존 컨테이너 삭제, 데이터 볼륨은 유지
새 DB 컨테이너   -> 기존 데이터 볼륨 연결
```

새 DB 컨테이너가 기존 데이터를 사용하려면 같은 볼륨을 올바른 데이터 경로에 연결해야 한다. DB 버전과 데이터 형식의 호환성도 충족해야 하므로, 볼륨이 남아 있다는 것만으로 임의의 DB 버전에서 사용할 수 있는 것은 아니다.

| 작업 | 컨테이너 내부 쓰기 영역 | 별도로 유지한 볼륨 |
| --- | --- | --- |
| 컨테이너 종료 | 남아 있음 | 남아 있음 |
| 컨테이너 삭제 | 제거됨 | 함께 삭제하지 않았다면 남아 있음 |
| 볼륨 삭제 | 별개 영역임 | 해당 볼륨 데이터 제거 |

볼륨 삭제 후 같은 이름으로 다시 만들어도 기존 데이터가 복원되지는 않는다. 이름이 같을 뿐 새 저장 공간이다. Docker 볼륨은 컨테이너와 별도의 수명을 가지며, 별도 삭제 작업의 대상이 된다. [Docker 공식 문서: Volumes](https://docs.docker.com/engine/storage/volumes/)

### 볼륨은 백업이 아니다

볼륨은 데이터를 유지하는 저장 공간이고, 백업은 데이터가 삭제되거나 손상됐을 때 복원할 사본이다. 볼륨 자체가 삭제되거나 저장 장치가 손상되면 별도 백업이나 스냅샷 등이 있어야 복원할 수 있다.

Coolify의 관리 설정과 실제 앱 데이터도 구분해야 한다. Coolify 자체 DB의 백업만으로 앱의 DB 데이터와 볼륨까지 보관되는 것은 아니다. [Coolify 공식 문서: How Coolify works](https://coolify.io/docs/core/how-coolify-works)

## 5. 정리

이미지는 앱 실행에 필요한 파일과 기본 설정을 담고, 컨테이너는 그 이미지를 바탕으로 앱을 실행한다. 코드 변경은 새 이미지에 반영하고, 실행 설정은 앱이 읽는 환경변수로 분리할 수 있다.

네트워크는 컨테이너 사이의 통신 경로를 제공한다. 접속할 때는 대상 컨테이너의 주소와 내부 포트를 사용할지, 서버에 공개한 포트를 사용할지 구분해야 한다.

볼륨은 컨테이너 교체와 데이터 보존을 분리한다. 컨테이너를 다시 만들더라도 기존 볼륨을 유지해서 연결하면 데이터를 이어서 사용할 수 있지만, 볼륨 자체의 삭제나 손상에 대비하려면 별도 백업이 필요하다.

Coolify는 이 이미지, 실행 설정, 네트워크, 저장 공간을 바탕으로 배포를 관리한다. 따라서 배포 설정을 볼 때는 무엇을 실행하는지, 어떤 설정으로 실행하는지, 어디와 통신하는지, 어떤 데이터를 유지하는지를 구분해서 이해해야 한다.
